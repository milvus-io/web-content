    </button></h1><p>As a collection moves from development to production, its schema often changes. You might add scalar fields such as <code translate="no">source_uri</code> or <code translate="no">review_status</code> for filtering and application logic, add a new vector field for embeddings generated by your application, add a BM25 Function and its generated sparse vector field for lexical search over existing text, or remove fields and Functions that are no longer used. Alter Collection Schema lets you make supported field and Function changes in place instead of recreating the collection.</p>
<div class="alert note">
<p>This guide covers schema changes for user-defined fields and for Functions with their generated vector fields in managed collections. To add a field to an external collection, refer to <a href="/docs/alter-external-collection-schema.md">Alter External Collection Schema</a>. For field property changes, such as changing <code translate="no">max_length</code> on a <code translate="no">VARCHAR</code> field or <code translate="no">max_capacity</code> on an <code translate="no">ARRAY</code> field, refer to <a href="/docs/alter-collection-field.md">Alter Collection Field</a>. For dynamic field behavior, refer to <a href="/docs/enable-dynamic-field.md">Dynamic Field</a> and <a href="/docs/modify-collection.md">Modify Collection</a>.</p>
</div>

    </button></h2><p><strong>Add user-defined fields</strong></p>
<ul>
<li><p>Added user-defined fields must be nullable. Set <code translate="no">nullable=True</code> when calling <code translate="no">add_collection_field()</code>. For existing entities, the added field is <code translate="no">NULL</code> unless you add a scalar field with a <code translate="no">default_value</code>.</p></li>
<li><p>Adding user-defined scalar fields is supported in Milvus 2.6.x and later. Adding user-defined vector fields is supported in Milvus 2.6.18 and later.</p></li>
</ul>
<ul>
<li>Adding StructArray fields is supported in Milvus 3.0.0 and later. Added StructArray fields must be nullable.</li>
</ul>
<ul>
<li><p>Adding a sub-field to an existing StructArray field is supported in Milvus 3.0.6 and later. The added sub-field must allow element-level null (<code translate="no">nullable=True</code> on a scalar or vector sub-field, <code translate="no">element_nullable=True</code> on an array sub-field), cannot have a default value, and cannot be bound to an index in the same request.</p></li>
<li><p>Field names must be unique among fields in the collection.</p></li>
</ul>
<p><strong>Add a Function and its generated vector field</strong></p>
<ul>
<li><p>Each schema update can add only one Function and one generated vector field.</p></li>
<li><p>The supported Function determines the generated vector field type: <code translate="no">BM25</code> generates a <code translate="no">SPARSE_FLOAT_VECTOR</code> field, and <code translate="no">MINHASH</code> generates a <code translate="no">BINARY_VECTOR</code> field.</p></li>
<li><p>The generated vector field must be a new field. It cannot point to a field that already exists in the collection schema.</p></li>
<li><p>The generated vector field cannot be nullable.</p></li>
<li><p>The input fields used by the Function must already exist in the collection.</p></li>
<li><p>When adding a BM25 or MinHash Function to an existing collection, the Function input must be a <code translate="no">VARCHAR</code> field. A <code translate="no">TEXT</code> input is not supported in this workflow because Milvus cannot backfill the generated output for existing entities from that input type.</p></li>
</ul>
<p><strong>Drop user-defined fields</strong></p>
<ul>
<li><p>You cannot drop the primary key field, partition key field, clustering key field, or the last vector field in a collection.</p></li>
<li><p>You can drop a whole <code translate="no">ARRAY&lt;STRUCT&gt;</code> field. Starting in Milvus 3.0.6, you can also drop an individual sub-field by its path, such as <code translate="no">chunks[lang]</code>, except the last sub-field of the <code translate="no">ARRAY&lt;STRUCT&gt;</code> field.</p></li>
<li><p>You cannot directly drop a field that is used as a Function input field or generated as a Function output field. To remove a Function output field, drop the Function that generates it.</p></li>
</ul>
<p><strong>Drop a Function and its generated vector field</strong></p>
<ul>
<li><p>In this schema-change workflow, dropping a Function removes the Function, its generated vector field, and the associated index. The Function input fields remain in the collection schema.</p></li>
<li><p>Dropping a Function is rejected if removing its generated vector field would leave the collection without any vector field.</p></li>
</ul>
<div class="alert note">
<p>For schema changes outside supported add and drop operations, recreate or migrate the collection.</p>
</div>

<ul>
<li><p><a href="#Add-user-defined-scalar-fields--Milvus-26x">Add user-defined scalar fields</a> when you need new metadata for filtering, query output, or application logic.</p></li>
<li><p><a href="#Add-StructArray-fields--Milvus-300">Add StructArray fields</a> when you need an array field whose elements share the same Struct schema.</p></li>
<li><p><a href="#Add-user-defined-vector-fields--Milvus-2618">Add user-defined vector fields</a> when your application generates embeddings and writes vector values to Milvus.</p></li>
<li><p><a href="#Add-a-Function-and-its-generated-vector-field--Milvus-30x">Add a Function and its generated vector field</a> when Milvus should generate vector values from existing fields, such as BM25 sparse vectors or MinHash signatures from text.</p></li>
</ul>
<ul>
<li><a href="#Add-a-sub-field-to-an-existing-StructArray-field--Milvus-306">Add a sub-field to an existing StructArray field</a> when existing Struct elements need a new attribute.</li>
</ul>
<p>In all cases, the new field name must not already exist in the collection, and the total number of fields cannot exceed the Milvus field-count limit. For details, refer to <a href="/docs/limitations.md#number-of-resources-in-a-collection">Milvus Limits</a>.</p>

    </button></h3><p>Use <code translate="no">add_collection_field()</code> to add a user-defined scalar field to an existing collection.</p>
<p>This differs from storing arbitrary keys in the dynamic field: after the schema update is available, the new scalar field becomes a regular part of the collection schema. You can insert or upsert values into it, create indexes on it where supported, use it in queries and search filters, and return it in query or search output.</p>
<p>Because existing entities were inserted before the new field existed, every added user-defined scalar field must be nullable:</p>
<ul>
<li><p>If you add a scalar field with <code translate="no">nullable=True</code> and no <code translate="no">default_value</code>, existing entities return <code translate="no">NULL</code> for the new field.</p></li>
<li><p>If you add a scalar field with <code translate="no">nullable=True</code> and <code translate="no">default_value</code>, existing entities return the default value instead of <code translate="no">NULL</code>.</p></li>
</ul>
<p>Scalar filter expressions do not match <code translate="no">NULL</code> scalar values. For details, refer to <a href="/docs/nullable-and-default.md">Nullable Fields</a>.</p>

<ul>
<li><p>A Function definition that reads from one or more existing input fields.</p></li>
<li><p>A new vector field that stores the Function output.</p></li>
<li><p>An index definition bound to the new vector field.</p></li>

<p>For example, a BM25 Function reads an existing <code translate="no">VARCHAR</code> field and generates a <code translate="no">SPARSE_FLOAT_VECTOR</code> field for lexical search. <div class="alert note">
<p>This feature requires Storage V3. For enablement instructions and compatibility considerations, see <a href="/docs/storage-v3.md">Storage V3</a>.</p>
</div>
<p>Adding a Function and its generated vector field to an existing collection also requires schema version compaction and storage version compaction. Milvus rejects the request if either setting is disabled. These additional prerequisites apply only when modifying an existing collection; defining the Function in the initial collection schema does not use this existing-data backfill workflow.</p>

<p>The generated vector field must not already exist in the collection, and it cannot be nullable. The Function input field must already exist.</p>
