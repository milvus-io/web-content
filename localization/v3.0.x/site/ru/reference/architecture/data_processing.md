    </button></h2><p>В Milvus можно выбрать количество шардов, используемых коллекцией — каждый шард сопоставляется с виртуальным каналом (<em>vchannel</em>). Как показано ниже, затем Milvus сопоставляет каждый <em>vchannel</em> с физическим каналом (<em>pchannel</em>), а каждый <em>pchannel</em> привязывается к конкретному потоковому узлу (Streaming Node).</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="/docs/v3.0.x/assets/pvchannel_wal.png" alt="VChannel, PChannel, and Streaming Node" class="doc-image" id="vchannel,-pchannel,-and-streaming-node" /> 
   <span>VChannel, PChannel и узел потоковой обработки</span>
  
 </span></p>
<p>После проверки данных прокси-сервер разбивает записываемое сообщение на отдельные пакеты данных для шардов в соответствии с заданными правилами маршрутизации по шардам.</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="https://milvus-docs.s3.us-west-2.amazonaws.com/assets/channels_1.png" alt="Channels 1" class="doc-image" id="channels-1" /> 
   <span>Каналы 1</span>
  
 </span></p>
<p>Затем записанные данные одного фрагмента (<em>vchannel</em>) отправляются в соответствующий узел потоковой обработки <em>pchannel</em>.</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="https://milvus-docs.s3.us-west-2.amazonaws.com/assets/written_data_flow.png" alt="write flow" class="doc-image" id="write-flow" /> 
   <span>Поток записи</span>
  
 </span></p>
<p>Узел потоковой обработки присваивает каждому пакету данных метку времени (TSO) для установления полного порядка операций. Он выполняет проверки согласованности полезной нагрузки перед записью её в базовый журнал предварительной записи (WAL). Как только данные надежно зафиксированы в WAL, их сохранность гарантирована — даже в случае сбоя узел потоковой обработки может воспроизвести WAL, чтобы полностью восстановить все незавершенные операции.</p>
<p>В то же время узел потоковой передачи асинхронно разбивает зафиксированные записи WAL на отдельные сегменты. Существует два типа сегментов:</p>
<ul>
<li><strong>Растущий сегмент</strong>: любые данные, которые ещё не были сохранены в объектном хранилище.</li>
<li><strong>Запечатанный сегмент</strong>: все данные сохранены в объектном хранилище; данные запечатанного сегмента являются неизменяемыми.</li>
</ul>
<p>Переход растущего сегмента в запечатанный сегмент называется сбросом. Узел потоковой передачи запускает сброс, как только он примет и запишет все доступные записи WAL для этого сегмента — то есть когда в базовом журнале предварительной записи больше не останется отложенных записей — после чего сегмент финализируется и оптимизируется для чтения.</p>

      </svg>
    </button></h2><p>Построение индекса выполняется узлом данных. Чтобы избежать частого построения индекса при обновлении данных, коллекция в Milvus дополнительно делится на сегменты, каждый из которых имеет свой собственный индекс.</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="https://milvus-docs.s3.us-west-2.amazonaws.com/assets/index_building.png" alt="Index building" class="doc-image" id="index-building" /> 
   <span>Построение индекса</span>
  
 </span></p>
<p>Milvus поддерживает построение индекса для каждого векторного поля, скалярного поля и первичного поля. Как входные, так и выходные данные при построении индекса взаимодействуют с объектным хранилищем: узел данных загружает в память снимки журнала для индексирования из сегмента (находящегося в объектном хранилище), десериализует соответствующие данные и метаданные для построения индекса, сериализует индекс по завершении построения и записывает его обратно в объектное хранилище.</p>
<p>Построение индекса в основном включает векторные и матричные операции и, следовательно, является вычислительно- и памятоемким процессом. Векторы нельзя эффективно индексировать с помощью традиционных деревовидных индексов из-за их высокомерности, но их можно индексировать с помощью более зрелых в этой области методов, таких как кластерные или графовые индексы. Независимо от типа, построение индекса для векторов большого размера сопряжено с огромным объёмом итерационных вычислений, таких как алгоритм K-средних или обход графа.</p>
<p>В отличие от индексирования скалярных данных, при построении векторного индекса необходимо в полной мере использовать преимущества ускорения SIMD (одна инструкция, несколько данных). Milvus имеет встроенную поддержку наборов инструкций SIMD, например SSE, AVX2 и AVX512. Учитывая «заминки» и ресурсоемкость построения векторных индексов, эластичность приобретает для Milvus решающее значение с экономической точки зрения. В будущих версиях Milvus будут продолжены исследования в области гетерогенных вычислений и бессерверных вычислений с целью снижения связанных с этим затрат.</p>
<p>Кроме того, Milvus также поддерживает скалярную фильтрацию и запросы по основному полю. Он имеет встроенные индексы для повышения эффективности запросов, например, индексы фильтра Блума, хеш-индексы, деревовидные индексы и инвертированные индексы, а также планирует внедрить дополнительные внешние индексы, такие как растровые индексы и индексы приближённого поиска.</p>

      </svg>
    </button></h2><p>Запрос данных — это процесс поиска в заданной коллекции <em>k</em> векторов, ближайших к целевому вектору, или <em>всех</em> векторов, находящихся в заданном диапазоне расстояний от этого вектора. Векторы возвращаются вместе с соответствующими первичными ключами и полями.</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="https://milvus-docs.s3.us-west-2.amazonaws.com/assets/data_query.jpg" alt="Data query" class="doc-image" id="data-query" /> 
   <span>Запрос данных</span>
  
 </span></p>
<p>Коллекция в Milvus разбита на несколько сегментов; узел потоковой обработки (Streaming Node) загружает растущие сегменты и поддерживает данные в режиме реального времени, в то время как узлы запросов (Query Nodes) загружают запечатанные сегменты.</p>
<p>При поступлении запроса на поиск прокси-сервер рассылает его всем потоковым узлам, отвечающим за соответствующие фрагменты, для одновременного выполнения поиска.</p>
<p>При поступлении запроса прокси одновременно запрашивает потоковые узлы, содержащие соответствующие фрагменты, на выполнение поиска.</p>
<p>Каждый узел потоковой обработки генерирует план запроса, выполняет поиск в своих локальных растущих данных и одновременно связывается с удаленными узлами запросов для получения исторических результатов, а затем агрегирует их в единый результат по фрагменту.</p>
<p>Наконец, прокси собирает все результаты по фрагментам, объединяет их в итоговый результат и возвращает его клиенту.</p>
<p><span class="img-wrapper">
  
   <img translate="no" src="https://milvus-docs.s3.us-west-2.amazonaws.com/assets/handoff.png" alt="Handoff" class="doc-image" id="handoff" /> 
   <span>Передача</span>
  
 </span></p>
<p>Когда растущий сегмент на потоковом узле сбрасывается в запечатанный сегмент — или когда узел данных завершает уплотнение — координатор инициирует операцию передачи, чтобы преобразовать эти растущие данные в исторические. Затем координатор равномерно распределяет запечатанные сегменты по всем узлам запросов, балансируя использование памяти, нагрузку на ЦП и количество сегментов, а также освобождает любые избыточные сегменты.</p>
