<p>Мы рады объявить о выпуске Milvus v3.0.3! В этом выпуске реализована поддержка цепочек функций (Function Chain) в гибридном поиске, частичное обновление на уровне элементов для полей Array, Struct и JSON, а также фильтрация по типу « <code translate="no">IS NULL</code> » для векторных полей, допускающих значение null, наряду с усилением безопасности и обширным набором исправлений, повышающих стабильность; обратите внимание на изменения, приводящие к несовместимости с предыдущими версиями, в устаревших REST-маршрутах V1 в порту метрик, правах на импорт бинарных журналов (binlog) и режиме доступа по умолчанию для продюсера Pulsar.</p>

<li>Добавлена поддержка цепочек функций (Function Chain) в гибридном поиске, что позволяет цепочке L2 верхнего уровня, начинающейся с выражения « <code translate="no">merge</code> », определять слияние и переранжирование, а также позволяет каждому подпоиску запускать собственную цепочку L0/L1 перед слиянием (<a href="https://github.com/milvus-io/milvus/pull/53541">#53541</a>)</li>
<li>Добавлена поддержка замены отдельных элементов массива, элементов массива структур или их подполей, а также путей JSON при частичных обновлениях; доступно в Go SDK и REST v2 (<a href="https://github.com/milvus-io/milvus/pull/53746">#53746</a>)</li>
<li>Добавлена поддержка динамических полей в цепочках функций при поиске и гибридном поиске (<a href="https://github.com/milvus-io/milvus/pull/54011">#54011</a>)</li>
<li>Добавлена поддержка выражений фильтрации <code translate="no">IS NULL</code> и <code translate="no">IS NOT NULL</code> для полей вектора, допускающих значение null, с пакетной проверкой допустимости для эффективного вычисления (<a href="https://github.com/milvus-io/milvus/pull/54020">#54020</a>)</li>
</ul>

    </button></h3><ul>
<li>Добавлена опциональная аутентификация root для конечных точек управления на порте метрик (<code translate="no">common.security.adminAuthEnabled</code>, отключена по умолчанию), а также удалены учетные данные и другие конфиденциальные значения из дампов конфигурации, HTTP-ответов и журналов (<a href="https://github.com/milvus-io/milvus/pull/53499">#53499</a>)</li>
<li>Сохранены первичные ключи существующих сущностей при полном обновлении-вставке (upsert) в коллекциях с автоидентификацией (AutoID), при этом новые ID назначаются только тем ключам, которые не найдены; для таких операций обновления-вставки теперь требуется загрузка коллекции (<a href="https://github.com/milvus-io/milvus/pull/53511">#53511</a>)</li>
<li>Добавлены алгоритмы сжатия gRPC snappy и s2, сделана настраиваемой кодировка zstd, а также усилена защита декомпрессии gRPC от выделения памяти чрезмерного размера (<a href="https://github.com/milvus-io/milvus/pull/53598">#53598</a>)</li>
<li>Заблокированы пути импорта, указывающие на внутренние каталоги хранения Milvus, и введено требование наличия нового права доступа на уровне кластера « <code translate="no">ImportBinlog</code> » для импорта из бинарных журналов (<code translate="no">backup=true</code>) и L0; это приводит к сбою работы ролей, не являющихся административными, которые обладают только правом доступа на уровне коллекции « <code translate="no">Import</code> », пока им не будет предоставлено право « <code translate="no">ImportBinlog</code> » (<a href="https://github.com/milvus-io/milvus/pull/53680">#53680</a>)</li>
<li>Оптимизирована запись наборов битов при поиске по индексам на базе Tantivy, что ускорило запись смежных идентификаторов документов примерно в 7 раз в микротестах (<a href="https://github.com/milvus-io/milvus/pull/53700">#53700</a>)</li>
<li>Уменьшено количество избыточных копий полезных данных и метаданных в пути выполнения запросов на C++ (<a href="https://github.com/milvus-io/milvus/pull/53756">#53756</a>)</li>
<li>Отложена загрузка статистики JSON для запечатанных сегментов до первого использования при отключенной разминке, так что сегменты, статистика JSON которых никогда не запрашивается, больше не несут затрат на загрузку (<a href="https://github.com/milvus-io/milvus/pull/53888">#53888</a>)</li>
<li>Добавлена опциональная предварительная проверка QueryCoord, которая оценивает потребность в памяти и локальном диске перед загрузкой коллекций или партиций, с показателями потребности для каждой группы ресурсов (<a href="https://github.com/milvus-io/milvus/pull/53905">#53905</a>)</li>
<li>Уменьшены накладные расходы на каждый фрагмент в выражениях фильтров и поиске по группировке в запечатанных сегментах за счет чтения данных через закреплённый в запросе снимок столбца (<a href="https://github.com/milvus-io/milvus/pull/53984">#53984</a>)</li>
<li>Ускорено декодирование RPC protobuf с помощью декодера fastPB для путей поиска, запроса, вставки и upsert; включено по умолчанию и управляется через <code translate="no">common.enableFastPB</code> (<a href="https://github.com/milvus-io/milvus/pull/53995">#53995</a>, <a href="https://github.com/milvus-io/milvus/pull/54003">#54003</a>)</li>
<li>Удалены устаревшие REST-маршруты <code translate="no">/api/v1/*</code> без подчеркивания (включая <code translate="no">/api/v1/health</code>) из порта метрик и добавлен <code translate="no">proxy.http.enableV1</code> для отключения оставшихся API версии 1; это изменение, нарушающее совместимость, поэтому клиентам следует перейти на REST API версии 2 или SDK gRPC и использовать <code translate="no">/healthz</code> или <code translate="no">/livez</code> для проверок работоспособности (<a href="https://github.com/milvus-io/milvus/pull/54028">#54028</a>)</li>
<li>Закрепили стеммер анализатора независимо от Tantivy, чтобы встроенные и пользовательские анализаторы продолжали генерировать одинаковые токены со стеммингом для существующих текстовых индексов при обновлениях Tantivy (<a href="https://github.com/milvus-io/milvus/pull/54097">#54097</a>)</li>
<li>Уменьшена задержка в выдаче завершенных результатов асинхронного segcore при высокой нагрузке на исполнители, благодаря чему готовые результаты выдаются быстрее, а не ожидают своей очереди в списке задач (<a href="https://github.com/milvus-io/milvus/pull/54127">#54127</a>)</li>
</ul>

<li>Исправлена проблема, при которой двухфазное задание импорта с « <code translate="no">timeout</code> », срок действия которого истек во время фиксации, завершалось с ошибкой и откатывалось, удаляя данные, которые уже были доступны для запросов, а также проблема, при которой отмена задания импорта не останавливала его выполняющиеся задачи на DataNodes (<a href="https://github.com/milvus-io/milvus/pull/53481">#53481</a>)</li>
<li>Исправлена проблема, при которой при использовании Pulsar в качестве WAL узел StreamingNode мог продолжать запись в канал после того, как его перенял другой узел, что приводило к потере зафиксированных строк; теперь по умолчанию в качестве <code translate="no">pulsar.producerAccessMode</code> используется <code translate="no">exclusive</code>, что требует Pulsar версии 2.8.0 или более поздней (<a href="https://github.com/milvus-io/milvus/pull/53539">#53539</a>)</li>
<li>Исправлена проблема, из-за которой автономная версия Milvus, развернутая с помощью Docker Compose или <code translate="no">standalone_embed.sh</code>, могла не записывать данные в каталоги данных с привязкой, принадлежащие пользователю root, как при новой установке, так и при обновлении (<a href="https://github.com/milvus-io/milvus/pull/53564">#53564</a>, <a href="https://github.com/milvus-io/milvus/pull/53615">#53615</a>)</li>
<li>Исправлена проблема, из-за которой поиск по растущим сегментам с промежуточным индексом мог периодически завершаться с ошибками reduce при одновременной вставке данных (<a href="https://github.com/milvus-io/milvus/pull/53574">#53574</a>)</li>
<li>Исправлена проблема, из-за которой StreamingNode мог использовать неверный режим Woodpecker, если <code translate="no">AlterWAL</code> запускался сразу после обновления конфигурации хранилища Woodpecker, что приводило к зависанию восстановления WAL после следующего перезапуска (<a href="https://github.com/milvus-io/milvus/pull/53584">#53584</a>)</li>
<li>Исправлена проблема, из-за которой вставка данных в коллекции с полями геометрии могла замирать при длительной нагрузке от GIS-запросов, если был включен кэш геометрии (<a href="https://github.com/milvus-io/milvus/pull/53609">#53609</a>)</li>
<li>Исправлена проблема, при которой Milvus мог зависать во время завершения работы или блокироваться на вызовах ведения журнала, если вывод журнала застревал (<a href="https://github.com/milvus-io/milvus/pull/53625">#53625</a>)</li>
<li>Исправлена проблема, из-за которой обновление внешней коллекции из недействительного источника снимков Milvus или из метаданных снимков, имеющих некорректный формат или использующих неподдерживаемую версию, не завершалось с ошибкой сразу и могло оставаться в состоянии ожидания до истечения таймаута (<a href="https://github.com/milvus-io/milvus/pull/53695">#53695</a>, <a href="https://github.com/milvus-io/milvus/pull/54034">#54034</a>)</li>
<li>Исправлена проблема, при которой запросы LIKE, содержащие символы NUL в полях с индексацией ngram, могли приводить к сбою QueryNode или возвращать некорректные совпадения (<a href="https://github.com/milvus-io/milvus/pull/53711">#53711</a>)</li>
<li>Исправлена проблема, при которой конечная точка проверки работоспособности сообщала о готовности узла до того, как все его компоненты завершили регистрацию (<a href="https://github.com/milvus-io/milvus/pull/53735">#53735</a>)</li>
<li>Исправлена проблема, из-за которой при загрузке коллекции могло отображаться сообщение о завершении, при этом пропускались восстановленные сегменты, имевшие только зафиксированный манифест V3, в результате чего их данные отсутствовали в результатах запросов (<a href="https://github.com/milvus-io/milvus/pull/53782">#53782</a>)</li>
<li>Исправлена проблема, при которой копирование снимков крупных объектов (около 2 ГБ) между бакетами могло завершаться таймаутом в OSS; объекты, размер которых превышает новый настраиваемый размер блока копирования ( <code translate="no">minio.multipartCopyThreshold</code> ) (по умолчанию 1 ГБ), теперь копируются с помощью многочастного копирования на стороне сервера (<a href="https://github.com/milvus-io/milvus/pull/53789">#53789</a>)</li>
<li>Исправлена проблема, из-за которой операции со снимками (создание, удаление, фиксация, отмена фиксации, экспорт и восстановление) могли ограничиваться или отклоняться из-за ограничений скорости DDL коллекции и принудительного запрета DDL (<a href="https://github.com/milvus-io/milvus/pull/53791">#53791</a>)</li>
<li>Исправлена проблема, из-за которой при импорте из Parquet для строк с нулевыми значениями в полях Timestamptz, допускающих нулевые значения, сохранялось значение NULL вместо значения по умолчанию для поля (<a href="https://github.com/milvus-io/milvus/pull/53808">#53808</a>)</li>
<li>Исправлена проблема, из-за которой реранкеры на основе моделей могли присваивать оценки не тем документам, когда служба реранкинга возвращала результаты в другом порядке, что приводило к некорректному ранжированию результатов поиска (<a href="https://github.com/milvus-io/milvus/pull/53813">#53813</a>)</li>
<li>Исправлена проблема, из-за которой запросы на поиск и запросы могли завершаться с ошибкой « <code translate="no">collection not loaded</code> » в течение длительного периода времени после перераспределения канала на другой QueryNode (<a href="https://github.com/milvus-io/milvus/pull/53814">#53814</a>)</li>
<li>Исправлена проблема, при которой групповой поиск со строгим ограничением на размер группы мог возвращать группы с меньшим количеством результатов, чем <code translate="no">group_size</code>, даже при наличии достаточного количества соответствующих объектов (<a href="https://github.com/milvus-io/milvus/pull/53899">#53899</a>)</li>

<li>Исправлена проблема, при которой функция « <code translate="no">phrase_match</code> » могла находить документы, содержащие повторяющийся термин запроса только один раз; производительность поиска по фразам была улучшена за счет обновления Tantivy (<a href="https://github.com/milvus-io/milvus/pull/54030">#54030</a>)</li>

    </button></h3><h4 id="External-Collection-more-complete-lakehouse-workflows" class="common-anchor-header">Внешняя коллекция: более полные рабочие процессы lakehouse</h4><p>В версии 3.0-beta была представлена функция «Внешняя коллекция»: возможность ссылаться на файлы озера данных на месте, создавать индексы и выполнять поиск по ним без копирования данных в Milvus. В этом выпуске эта функция расширена до полноценных рабочих процессов поиска в архитектуре «lakehouse». Внешние поля теперь могут служить входными данными для полей, генерируемых функциями, таких как разреженные векторы BM25, сигнатуры MinHash и текстовые вложения, благодаря чему поля поиска, основанные на тексте и результатах моделирования, создаются внутри Milvus без копирования исходной таблицы. Функция обновления также поддерживает аддитивную эволюцию схемы: когда во внешней таблице появляются новые столбцы, Milvus обновляет затронутые сегменты вместо перестроения коллекции.</p>
<p>В этом выпуске также добавлен внешний формат « <code translate="no">milvus-table</code> », который рассматривает метаданные Milvus Snapshot и манифесты Storage V3 в качестве внешнего источника, благодаря чему сам снимок коллекции может выступать в качестве внешней таблицы — системы пакетной обработки и предоставления данных получают общий, основанный на манифесте вид одних и тех же данных.</p>
<p>Дополнительную информацию см. в разделах <a href="/docs/ru/create-an-external-collection.md">«Создание внешней коллекции</a> » и <a href="/docs/ru/snapshots.md">«Снимки</a>».</p>
<h4 id="Flexible-schema-add-backfill-and-drop-columns-online" class="common-anchor-header">Гибкая схема: добавление, заполнение и удаление столбцов в режиме реального времени</h4><p>В производственной среде схемы не остаются неизменными — модели встраивания заменяются, признаки итеративно обновляются, поля становятся устаревшими — и раньше это означало полную перестройку коллекции с простоями или двойной записью. Версия 3.0.0 замыкает цикл: столбцы можно добавлять, заполнять и удалять без прерывания обслуживания.</p>
<p>Заполнение данных работает в обоих направлениях. Внешнее заполнение обрабатывает значения, вычисленные вне Milvus: добавьте столбец, создайте моментальный снимок коллекции в качестве согласованной исходной точки, запустите задание в автономном режиме, запишите значения обратно, и Milvus индексирует новый столбец инкрементально — обновление модели встраивания для сотен миллионов строк становится «горячим» процессом без простоев. Внутреннее пополнение охватывает значения, полученные с помощью ядра: присоедините функцию BM25 или MinHash к существующей коллекции, и её поле вывода будет автоматически вычисляться на основе имеющихся данных.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/add-fields-to-an-existing-collection.md">«Добавление полей в существующую коллекцию</a>».</p>
<h4 id="Sparse-index-overhaul-SINDI-Block-Max-WAND-and-Block-Max-MaxScore" class="common-anchor-header">Переработка индекса разреженных данных: SINDI, Block-Max WAND и Block-Max MaxScore</h4><p>В Milvus 3.0 полностью обновлен индекс разреженных векторов. В него внедрены новые алгоритмы поиска — <a href="https://arxiv.org/abs/2509.08395">SINDI</a>, Block-Max WAND и Block-Max MaxScore — наряду с сжатием инвертированного списка, настраиваемой квантованием и выбором алгоритма поиска для каждой рабочей нагрузки. Также оптимизированы загрузка через mmap, сериализация и подсчёт результатов по алгоритму BM25, что сокращает объём хранения индекса и накладные расходы на загрузку при крупномасштабном поиске по разреженным векторам и полнотекстовом поиске. По результатам внутренних тестов сжатый индекс BM25 примерно в 3 раза меньше, чем разреженный индекс 2.6, при сопоставимом коэффициенте восстановления, а SINDI достигает примерно 10-кратного превышения QPS по сравнению с MaxScore при использовании обученных разреженных вложений. После включения новой версии индекса (см. «Примечания по совместимости и поведению») SINDI становится стандартным алгоритмом для поиска по разреженным IP, а MaxScore — для BM25.</p>
<h4 id="StructArray-coverage" class="common-anchor-header">Расширение поддержки StructArray</h4><p>StructArray теперь поддерживает нулевые значения, битовые индексы, динамическое добавление полей в активные коллекции и частичное обновление полей структур посредством операции upsert, а также соответствующие возможности REST и массового импорта.</p>
<p>Поиск на уровне элементов теперь включает гибридный поиск по подполям векторов с настраиваемым сворачиванием данных по объектам (варианты max / sum / avg / top-k), а также поиск по диапазону и группировку внутри него. Вложенная фильтрация поддерживает предикаты <code translate="no">element_filter</code>, кванторы <code translate="no">MATCH_ANY</code> / <code translate="no">MATCH_ALL</code> / <code translate="no">MATCH_LEAST</code> / <code translate="no">MATCH_MOST</code> / <code translate="no">MATCH_EXACT</code>, позиционный доступ к подполям (например, <code translate="no">tags[0][name]</code>) и операторы <code translate="no">array_length()</code> для столбцов структуры.</p>
<p>Дополнительные сведения см. в разделах <a href="/docs/ru/array-of-structs.md">«StructArray</a> » и <a href="/docs/ru/struct-array-operators.md">«Операторы StructArray</a>».</p>
<h4 id="Search-Aggregation-and-faceted-search" class="common-anchor-header">Агрегация результатов поиска и фасетный поиск</h4><p>Агрегация запросов из бета-версии вычисляет точные статистические данные по отфильтрованным данным; в версии 3.0.0 добавлен фасетированный поиск в поисковом пути. Укажите поле фасета во время поиска, и Milvus вернет ведущие значения фасета, каждое из которых представлено элементом, наилучшим образом соответствующим ранжированию ANN, и аннотировано агрегатами, такими как COUNT и AVG — боковая панель фасетного поиска (бренд, ценовой диапазон, атрибуты) в одном запросе, вместо избыточного извлечения и подсчёта на стороне клиента.</p>
<h4 id="Function-Chain-reranking" class="common-anchor-header">Переранжирование с помощью цепочки функций</h4><p>Переранжирование теперь можно компоновать с помощью API «Цепочки функций», который выполняет упорядоченный типизированный конвейер в рамках одного поискового запроса. Цепочка может объединять раннее переоценки L0 на QueryNode с переранжированием L2 после редукции на Proxy, поддерживая преобразование и комбинирование оценок, переранжирование на основе моделей, сортировку и отсев кандидатов без оркестрации на стороне клиента. В этом выпуске также добавлено встроенное подсчёт оценок XGBoost для переранжирования L0 с использованием моделей UBJ, зарегистрированных как FileResources, а также провайдеры инференции Hugging Face для управляемого сервером встраивания текста и переранжирования по сходству предложений.</p>
<h4 id="TEXT-long-text-fields" class="common-anchor-header">Поля TEXT для длинных текстов</h4><p>Поля TEXT обеспечивают полноценную поддержку длинных текстов, устраняя ограничения на длину со стороны хранилища: они поддерживают алгоритмы « <code translate="no">text_match</code> », « <code translate="no">phrase_match</code> » и BM25. Значения размером до 64 КБ хранятся непосредственно в столбце; более крупные значения перемещаются в файлы LOB на уровне партиций в формате Vortex, при этом в столбце хранятся только ссылки <code translate="no">(file_id, offset)</code>. Файлы LOB используются совместно всеми сегментами, поэтому при уплотнении перемещаются ссылки, а не переписывается текст. Для RAG это означает извлечение векторов и исходного текста из одного и того же хранилища за один операцию ввода-вывода — не требуется использование внешнего хранилища BLOB.</p>
<h4 id="FAISS-index-passthrough" class="common-anchor-header">Пропуск индекса FAISS</h4><p>Новый тип индекса « <code translate="no">FAISS</code> » принимает произвольные строки-фабрики индексов Faiss через параметр <code translate="no">faiss_index_name</code> — <code translate="no">IVF64,Flat</code>, <code translate="no">HNSW16,Flat</code>, <code translate="no">OPQ16,IVF64,PQ16x4</code> — с передачей параметров поиска, благодаря чему рецепты Faiss воспроизводятся непосредственно в Milvus.</p>
<h4 id="Vortex-and-Lance-format-support" class="common-anchor-header">Поддержка форматов Vortex и Lance</h4><p>Уровень хранения пополняется двумя открытыми столбчатыми форматами: Vortex в качестве внутреннего формата нового поколения — с адаптивными кодировками (словарная, RLE, упаковка битов, сжатие с учетом типов с плавающей запятой), распаковкой без копирования, оптимизированным для смешанных векторно-скалярных рабочих нагрузок — и Lance наряду с Parquet для обмена данными в открытой экосистеме. Vortex станет внутренним форматом по умолчанию; в планах развития предусмотрены спуск фильтров и локальный вариант.</p>
<h4 id="Woodpecker-standalone-deployment" class="common-anchor-header">Автономное развертывание Woodpecker</h4><p>Woodpecker, журнал WAL, лежащий в основе потокового пути записи, теперь можно развертывать как независимый сервис, а не встраивать в другие узлы — с независимым масштабированием, изоляцией неисправностей и наблюдаемостью, как любой другой микросервис. Это особенно важно для крупных кластеров и рабочих нагрузок с высокой интенсивностью записи.</p>

<p>Функция «Внешний сбор» устраняет необходимость копирования. Коллекция Milvus может ссылаться на файлы там, где они уже находятся, а Milvus управляет только схемой, индексами и выполнением запросов. Клиенты, чьи данные не могут покидать озеро данных (например, команды из сферы финансов и здравоохранения), могут выполнять векторный поиск по этим данным прямо там, где они находятся. Один набор данных, хранящийся в озере данных, также может одновременно обслуживаться несколькими экземплярами Milvus.</p>

<h4 id="Snapshot" class="common-anchor-header">Снимок</h4><p>Для обслуживания и пакетного обнаружения часто требуется одновременный доступ к одной и той же коллекции. Оценка A/B-моделей, крупномасштабная дедупликация, проверка заполнения пробелов и откат версий — все эти операции требуют стабильного представления коллекции, даже когда в нее продолжают записываться данные.</p>
<p>Снимки создают доступное только для чтения представление коллекции на определенный момент времени, ссылаясь на существующие сегменты вместо копирования данных, поэтому предельные затраты на хранение близки к нулю. Пакетные задания могут считывать данные из снимка в режиме изоляции типа MVCC, в то время как активная коллекция продолжает принимать записи.</p>
<p>Дополнительные сведения см. в разделах <a href="/docs/ru/snapshots.md">«Снимки</a>», <a href="/docs/ru/manage-snapshots.md">«Управление снимками</a>» и <a href="/docs/ru/snapshot-use-cases.md">«Варианты использования снимков</a>».</p>
<h4 id="Query--Search-Order-By" class="common-anchor-header">Запрос / Поиск с сортировкой</h4><p>Поиск и запросы теперь поддерживают сортировку по нескольким полям, при этом сортировка переносится в ядро Milvus, а параметры « <code translate="no">ASC</code> » и « <code translate="no">DESC</code> » можно настраивать для каждого поля. Это устраняет распространённый недостаток в производственной среде: ранжирование Top-K только по расстоянию часто не соответствует бизнес-потребностям, когда наиболее похожий элемент не является самым дешёвым, самым свежим или самым популярным.</p>
<p>Приложениям больше не нужно избыточно извлекать результаты и повторно сортировать их на стороне клиента для формирования составного ранжирования.</p>
<p>Дополнительную информацию см. в разделах <a href="/docs/ru/single-vector-search.md#Sort-Search-Results-by-Scalar-Fields--Milvus-30x">«Сортировка результатов поиска по скалярным полям</a> » и <a href="/docs/ru/get-and-scalar-query.md#Sort-Query-Results--Milvus-30x">«Сортировка результатов запросов</a>».</p>
<h4 id="Query-Aggregation" class="common-anchor-header">Агрегирование запросов</h4><p>Для формирования статистики распределения по арендаторам, подсчёта полноты полей или отслеживания хода развёртывания версий на основе коллекции Milvus ранее требовалось извлекать соответствующие сущности обратно на клиент и агрегировать их там. В Milvus 3.0 скалярная агрегация в стиле SQL перенесена в ядро. Вызов запроса принимает выражения типа « <code translate="no">group_by_fields</code> » и выражения агрегации в формате « <code translate="no">output_fields</code> », включая « <code translate="no">count(*)</code> », « <code translate="no">count(&lt;field&gt;)</code> », « <code translate="no">sum(&lt;field&gt;)</code> », « <code translate="no">avg(&lt;field&gt;)</code> », « <code translate="no">min(&lt;field&gt;)</code> » и « <code translate="no">max(&lt;field&gt;)</code> ». Агрегация вычисляется на стороне сервера после фильтрации.</p>
<p>Дополнительные сведения см. в разделе <a href="/docs/ru/get-and-scalar-query.md#Aggregate-Query-Results--Milvus-30x">«Агрегирование результатов запросов</a>».</p>
<h4 id="Null-Vector" class="common-anchor-header">Нулевой вектор</h4><p>Векторы часто генерируются асинхронно, поэтому сущность может поступить раньше, чем её вектор. В мультимодальных данных также встречаются естественные пробелы, например видео без субтитров или товар без изображения. В предыдущих версиях не было оптимального решения: приложения либо откладывали запись до готовности вектора, либо заполняли местозаполнителем, и оба варианта ухудшали качество поиска.</p>
<p>Milvus 3.0 поддерживает значение NULL в векторных полях для всех шести типов векторов. Поиск автоматически пропускает векторы с значением NULL, качество поиска при этом не ухудшается, а векторы с значением NULL практически не занимают места в хранилище. В рамках этого изменения функция « <code translate="no">AddField</code> » также распространяется на векторные поля: с помощью команды ` <code translate="no">nullable=True</code>` существующая коллекция может добавлять новые векторные поля в режиме онлайн без перестроения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/nullable-and-default.md">«Поля, допускающие значение NULL</a>».</p>
<h4 id="Custom-Dictionary--Synonym-Dictionary" class="common-anchor-header">Пользовательский словарь и словарь синонимов</h4><p>Готовые токенизаторы не всегда соответствуют требованиям к качеству поиска в производственной среде. Китайский язык, вертикальные области, такие как медицина, право и химия, а также многоязычные корпуса могут существенно выиграть от использования пользовательских словарей и таблиц синонимов. До сих пор эти ресурсы в основном использовались в виде переформулировок запросов на стороне приложения.</p>
<p>В Milvus 3.0 добавлен механизм FileResource для регистрации пользовательских словарей токенизаторов, списков синонимов, списков стоп-слов и правил декомпозиции сложных слов. После регистрации на ресурс можно ссылаться из любого токенизатора или фильтра, и он будет применяться в BM25, анализаторах и Text Match. Теперь словари и синонимы можно версионировать и централизованно управлять ими, вместо того чтобы они были разбросаны по коду приложения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/manage-file-resources.md">«Управление файловыми ресурсами</a>».</p>
<h4 id="Entity-TTL" class="common-anchor-header">Срок хранения сущностей (TTL)</h4><p>TTL на уровне коллекции и на уровне раздела слишком грубы для многих сценариев жизненного цикла и обеспечения соответствия требованиям. Различные арендаторы внутри одной и той же коллекции часто имеют разные правила хранения, и отдельные сущности могут нуждаться в истечении срока хранения по графику, не совпадающему с остальной частью коллекции.</p>
<p>Milvus 3.0 поддерживает TTL на уровне сущностей. Определите поле « <code translate="no">TIMESTAMPTZ</code> » в схеме, отметьте его как поле TTL с помощью свойства коллекции, и Milvus автоматически удалит просроченные сущности. Это позволяет обрабатывать запросы на «право на забвение», удалять просроченные данные сеанса и ограничивать историю переписки без необходимости очистки на стороне приложения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/set-collection-ttl.md#Set-entity-level-TTL--Milvus-30x">«Установка TTL на уровне сущности</a>».</p>
<h4 id="MinHash-DIDO-Doc-in-Doc-out" class="common-anchor-header">MinHash DIDO (Doc-in, Doc-out)</h4><p>В Milvus 2.6 был добавлен индекс <code translate="no">MINHASH_LSH</code> для обнаружения почти-дубликатов на основе множеств, но приложениям по-прежнему приходилось вычислять сигнатуры MinHash перед записью данных в Milvus.</p>
<p>В Milvus 3.0 добавлена функция MinHash, выполняемая на стороне сервера. Объявите в схеме поле ввода « <code translate="no">VARCHAR</code> » и поле вывода « <code translate="no">BINARY_VECTOR</code> », присоедините функцию « <code translate="no">FunctionType.MINHASH</code> », и Milvus будет вычислять сигнатуры во время вставки, массовой вставки и поиска. В сочетании с функцией « <code translate="no">MINHASH_LSH</code> » это обеспечивает поддержку рабочих процессов дедупликации для больших наборов данных, формирования отпечатков и обнаружения плагиата внутри Milvus.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/minhash-function.md">«Функция MinHash</a>».</p>
<h4 id="EmbList-+-DISKANN" class="common-anchor-header">EmbList + DISKANN</h4><p>Предположение «одна сущность = один вектор» больше не соответствует современному поиску. Длинные документы разбиваются на множество фрагментов, модели с поздним взаимодействием, такие как ColBERT, генерируют по одному вектору на каждый токен, а мультимодальные сущности могут иметь несколько представлений.</p>
<p>EmbList хранит список векторов переменной длины для каждого объекта, используя « <code translate="no">DISKANN</code> » в качестве индекса на диске. Использование дискового пространства позволяет контролировать потребление ОЗУ, когда объем корпуса превышает доступный объем памяти. EmbList + « <code translate="no">DISKANN</code> » — это первый вариант из более широкого семейства StructList в данной версии RC. Остальные элементы семейства, включая фильтрацию StructList и ускорение работы с несколькими векторами с помощью Muvera / Lemur, планируется включить в официальный релиз версии 3.0.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/search-with-embedding-lists.md">«Поиск с использованием списков вложений</a>».</p>
<h4 id="Force-Merge" class="common-anchor-header">Принудительное слияние</h4><p>В производственных рабочих нагрузках со временем накапливается фрагментация сегментов, что приводит к колебаниям задержки запросов и увеличению объёма хранилища.</p>
<p>В Milvus 3.0 добавлена возможность явного запуска уплотнения сегментов в периоды низкой нагрузки как в синхронном, так и в асинхронном режимах.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/force-merge.md">«Принудительная уплотнение слиянием</a>».</p>
<h4 id="Storage-V3" class="common-anchor-header">Хранилище V3</h4><p>В Milvus 3.0 представлен Storage V3 — столбчатый механизм хранения на основе манифестов, в котором данные и метаданные хранятся в объектном хранилище, совместимом с S3. Каждая версия набора данных фиксируется в виде неизменяемого моментального снимка манифеста — файла в кодировке Avro, в котором фиксируется, какие группы столбцов, дельта-журналы и статистические данные входят в состав набора данных.</p>
<p>Манифесты представляют собой компактные файлы Avro, а дельта-журналы фиксируют удаления на уровне сущностей без перезаписи файлов данных. Это позволяет свести накладные расходы на метаданные к минимуму по мере роста наборов данных. Манифест также отделяет отслеживание метаданных от пути запроса, что позволяет коллекции управлять большим количеством сегментов без ухудшения производительности запросов.</p>
<p>Поскольку состояния хранятся в объектном хранилище, набор данных является самоописательным: любой читатель, имеющий доступ к пути хранения, может обнаружить и интерпретировать его без центрального каталога. Это свойство лежит в основе интеграции с External Collection, Snapshot и будущими озерами данных.</p>
