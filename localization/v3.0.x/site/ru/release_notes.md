<p>Мы рады объявить о выпуске Milvus v3.0.1! В этом выпуске добавлены управление снимками REST v2, расширенные возможности переранжирования, а также поддержка поля TEXT в клиенте Go и RESTful API, наряду с улучшениями производительности и исправлениями для Storage V3, согласованности данных и безопасности.</p>

<li>Добавлено взвешенное переранжирование RRF с опциональными весами для каждого запроса ANN в FunctionScore, REST, устаревшем гибридном поиске и клиенте Go (<a href="https://github.com/milvus-io/milvus/pull/52891">#52891</a>, <a href="https://github.com/milvus-io/milvus/pull/52926">#52926</a>)</li>

<li>Улучшена безопасность памяти при обработке значений по умолчанию JSON и представлений строк, не завершающихся символом NUL (<a href="https://github.com/milvus-io/milvus/pull/52906">#52906</a>)</li>

    </button></h3><h4 id="External-Collection-more-complete-lakehouse-workflows" class="common-anchor-header">Внешняя коллекция: более полные рабочие процессы lakehouse</h4><p>В версии 3.0-beta была представлена функция «Внешняя коллекция»: возможность ссылаться на файлы озера данных на месте, создавать индексы и выполнять поиск по ним без копирования данных в Milvus. В данном выпуске эта функция расширена для обеспечения полноценных рабочих процессов поиска в «lakehouse». Внешние поля теперь могут служить входными данными для полей, генерируемых функциями, таких как разреженные векторы BM25, сигнатуры MinHash и текстовые вложения, благодаря чему поля поиска, основанные на тексте и результатах моделирования, создаются внутри Milvus без копирования исходной таблицы. Функция обновления также поддерживает аддитивную эволюцию схемы: когда во внешней таблице появляются новые столбцы, Milvus вносит исправления в затронутые сегменты вместо перестроения коллекции.</p>
<p>В этом выпуске также добавлен внешний формат « <code translate="no">milvus-table</code> », который рассматривает метаданные Milvus Snapshot и манифесты Storage V3 в качестве внешнего источника, благодаря чему сам снимок коллекции может использоваться в качестве внешней таблицы — пакетные и сервисные системы получают общий, основанный на манифесте вид одних и тех же данных.</p>
<p>Дополнительную информацию см. в разделах <a href="/docs/ru/create-an-external-collection.md">«Создание внешней коллекции</a> » и <a href="/docs/ru/snapshots.md">«Снимки</a>».</p>
<h4 id="Flexible-schema-add-backfill-and-drop-columns-online" class="common-anchor-header">Гибкая схема: добавление, заполнение и удаление столбцов в режиме реального времени</h4><p>В производственной среде схемы не остаются неизменными — модели встраивания заменяются, признаки итеративно обновляются, поля становятся устаревшими — и раньше это означало полную перестройку коллекции с простоем или двойной записью. Версия 3.0.0 замыкает цикл: столбцы можно добавлять, заполнять и удалять без остановки обслуживания.</p>
<p>Заполнение данных работает в обоих направлениях. Внешнее заполнение обрабатывает значения, вычисленные вне Milvus: добавьте столбец, создайте моментальный снимок коллекции в качестве согласованной отправной точки, запустите задание в автономном режиме, запишите значения обратно, и Milvus индексирует новый столбец постепенно — обновление модели встраивания для сотен миллионов строк становится «горячим» процессом без простоев. Внутреннее пополнение охватывает значения, полученные с помощью ядра: присоедините функцию BM25 или MinHash к существующей коллекции, и её выходное поле будет автоматически вычисляться на основе имеющихся данных.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/add-fields-to-an-existing-collection.md">«Добавление полей в существующую коллекцию</a>».</p>
<h4 id="Sparse-index-overhaul-SINDI-Block-Max-WAND-and-Block-Max-MaxScore" class="common-anchor-header">Переработка индекса разреженных данных: SINDI, Block-Max WAND и Block-Max MaxScore</h4><p>В Milvus 3.0 полностью обновлен индекс разреженных векторов. Внедрены новые алгоритмы поиска — <a href="https://arxiv.org/abs/2509.08395">SINDI</a>, Block-Max WAND и Block-Max MaxScore — наряду с сжатием инвертированного списка, настраиваемой квантованием и выбором алгоритма поиска для каждой рабочей нагрузки. Также оптимизированы загрузка через mmap, сериализация и подсчёт результатов по алгоритму BM25, что сокращает объём хранения индекса и накладные расходы на загрузку при крупномасштабном поиске по разреженным векторам и полнотекстовом поиске. По результатам внутренних тестов сжатый индекс BM25 примерно в 3 раза меньше, чем разреженный индекс 2.6, при сопоставимом коэффициенте восстановления, а SINDI достигает производительности (QPS) примерно в 10 раз выше, чем у MaxScore, при использовании обученных разреженных вложений. После включения новой версии индекса (см. «Примечания по совместимости и поведению») SINDI становится стандартным алгоритмом для поиска по разреженным IP-адресам, а MaxScore — для BM25.</p>
<h4 id="StructArray-coverage" class="common-anchor-header">Расширение поддержки StructArray</h4><p>StructArray теперь поддерживает нулевые значения, битовые индексы, динамическое добавление полей в активные коллекции и частичное обновление полей структур посредством операции upsert, а также соответствующие возможности REST и массового импорта.</p>
<p>Поиск на уровне элементов теперь включает гибридный поиск по подполям векторов с настраиваемым сворачиванием данных по объекту (варианты max / sum / avg / top-k), а также поиск по диапазону и группировку внутри него. Вложенная фильтрация поддерживает предикаты типа « <code translate="no">element_filter</code> », кванторы « <code translate="no">MATCH_ANY</code> » / « <code translate="no">MATCH_ALL</code> » / « <code translate="no">MATCH_LEAST</code> » / « <code translate="no">MATCH_MOST</code> » / « <code translate="no">MATCH_EXACT</code> », позиционный доступ к подполям (например, « <code translate="no">tags[0][name]</code> ») и оператор « <code translate="no">array_length()</code> » для столбца структуры.</p>
<p>Дополнительные сведения см. в разделах <a href="/docs/ru/array-of-structs.md">«StructArray</a> » и <a href="/docs/ru/struct-array-operators.md">«Операторы StructArray</a>».</p>
<h4 id="Search-Aggregation-and-faceted-search" class="common-anchor-header">Агрегация результатов поиска и фасетный поиск</h4><p>Агрегация запросов из бета-версии вычисляет точные статистические данные по отфильтрованным данным; версия 3.0.0 добавляет фасетирование в путь поиска. Укажите поле фасета во время поиска, и Milvus вернет ведущие значения фасета, каждое из которых представлено элементом, наиболее соответствующим ранжированию ANN, и снабжено агрегатами, такими как COUNT и AVG — боковая панель фасетного поиска (бренд, ценовой диапазон, атрибуты) в одном запросе, вместо избыточного извлечения и подсчёта на стороне клиента.</p>
<h4 id="Function-Chain-reranking" class="common-anchor-header">Переранжирование с помощью цепочки функций</h4><p>Переранжирование теперь можно компоновать с помощью API «Цепочки функций», который выполняет упорядоченный типизированный конвейер в рамках одного поискового запроса. Цепочка может объединять раннее переоценку L0 на QueryNode с переранжированием L2 после редукции на Proxy, поддерживая преобразование и комбинацию оценок, переранжирование на основе моделей, сортировку и отсев кандидатов без координации со стороны клиента. В этом выпуске также добавлено встроенное подсчёт оценок XGBoost для переранжирования L0 с использованием моделей UBJ, зарегистрированных в качестве FileResources, а также провайдеры инференции Hugging Face для управляемого сервером встраивания текста и переранжирования по сходству предложений.</p>
<h4 id="TEXT-long-text-fields" class="common-anchor-header">Поля TEXT для длинных текстов</h4><p>Поля TEXT обеспечивают полноценную поддержку длинных текстов, устраняя ограничения на длину на стороне хранилища: они поддерживают алгоритмы « <code translate="no">text_match</code> », « <code translate="no">phrase_match</code> » и «BM25». Значения размером до 64 КБ хранятся непосредственно в столбце; более крупные значения перемещаются в файлы LOB на уровне партиций в формате Vortex, при этом в столбце хранятся только ссылки <code translate="no">(file_id, offset)</code>. Файлы LOB используются совместно всеми сегментами, поэтому при уплотнении перемещаются ссылки, а не перезаписывается текст. Для RAG это означает извлечение векторов и исходного текста из одного и того же хранилища за один цикл ввода-вывода — не требуется использование внешнего хранилища BLOB.</p>
<h4 id="FAISS-index-passthrough" class="common-anchor-header">Пропуск индекса FAISS</h4><p>Новый тип индекса « <code translate="no">FAISS</code> » ( ) принимает произвольные строки-шаблоны для генерации индексов Faiss через параметр « <code translate="no">faiss_index_name</code> » — <code translate="no">IVF64,Flat</code>, <code translate="no">HNSW16,Flat</code>, <code translate="no">OPQ16,IVF64,PQ16x4</code> — с передачей параметров поиска, благодаря чему рецепты Faiss воспроизводятся непосредственно в Milvus.</p>
<h4 id="Vortex-and-Lance-format-support" class="common-anchor-header">Поддержка форматов Vortex и Lance</h4><p>Уровень хранения пополнился двумя открытыми столбчатыми форматами: Vortex в качестве внутреннего формата нового поколения — с адаптивными кодировками (словарная, RLE, упаковка битов, сжатие с учетом типов с плавающей запятой), распаковкой без копирования, оптимизированным для смешанных векторно-скалярных рабочих нагрузок — и Lance наряду с Parquet для обмена данными в рамках открытой экосистемы. Vortex станет внутренним форматом по умолчанию; в планах развития предусмотрены спуск фильтров и локальный вариант.</p>
<h4 id="Woodpecker-standalone-deployment" class="common-anchor-header">Автономное развертывание Woodpecker</h4><p>Woodpecker, журнал WAL, лежащий в основе конвейера потоковой записи, теперь можно развертывать как независимый сервис, а не встраивать в другие узлы — с независимым масштабированием, изоляцией неисправностей и наблюдаемостью, как и любой другой микросервис. Это особенно важно для крупных кластеров и рабочих нагрузок с высокой интенсивностью записи.</p>

<p>Функция «Внешний сбор» устраняет необходимость копирования. Коллекция Milvus может ссылаться на файлы там, где они уже находятся, а Milvus управляет только схемой, индексами и выполнением запросов. Инкрементное обновление обеспечивает синхронизацию коллекции с базовыми файлами. Клиенты, чьи данные не могут покидать «озеро» (например, команды из сферы финансов и здравоохранения), могут выполнять векторный поиск по этим данным прямо на месте их хранения. <h4 id="Snapshot" class="common-anchor-header">Снимок</h4><p>Для обслуживания и пакетного обнаружения часто требуется одновременный доступ к одной и той же коллекции. Оценка A/B-моделей, крупномасштабная дедупликация, проверка заполнения данных и откат версий — все эти операции требуют стабильного представления коллекции, даже когда в неё продолжают записываться данные.</p>
<p>Снимки создают доступное только для чтения представление коллекции на определенный момент времени, ссылаясь на существующие сегменты вместо копирования данных, поэтому предельные затраты на хранение близки к нулю. Пакетные задания могут считывать данные из снимка в режиме изоляции типа MVCC, в то время как активная коллекция продолжает принимать записи.</p>
<p>Дополнительные сведения см. в разделах <a href="/docs/ru/snapshots.md">«Снимки</a>», <a href="/docs/ru/manage-snapshots.md">«Управление снимками</a>» и <a href="/docs/ru/snapshot-use-cases.md">«Варианты использования снимков</a>».</p>
<h4 id="Query--Search-Order-By" class="common-anchor-header">Запрос / Поиск с сортировкой</h4><p>Поиск и запросы теперь поддерживают сортировку по нескольким полям, при этом сортировка переносится в ядро Milvus, а параметры « <code translate="no">ASC</code> » и « <code translate="no">DESC</code> » можно настраивать для каждого поля. Это устраняет распространенную проблему в производственной среде: ранжирование Top-K только по расстоянию часто не соответствует бизнес-потребностям, когда наиболее похожий элемент не является самым дешевым, самым свежим или самым популярным.</p>
<p>Приложениям больше не нужно избыточно извлекать результаты и повторно сортировать их на стороне клиента для формирования составного ранжирования.</p>
<p>Дополнительную информацию см. в разделах <a href="/docs/ru/single-vector-search.md#Sort-Search-Results-by-Scalar-Fields--Milvus-30x">«Сортировка результатов поиска по скалярным полям</a> » и <a href="/docs/ru/get-and-scalar-query.md#Sort-Query-Results--Milvus-30x">«Сортировка результатов запросов</a>».</p>
<h4 id="Query-Aggregation" class="common-anchor-header">Агрегирование запросов</h4><p>Для формирования статистики распределения арендаторов, подсчёта полноты полей или отслеживания хода развёртывания версий на основе коллекции Milvus ранее требовалось извлекать соответствующие сущности обратно на клиент и агрегировать их там. В Milvus 3.0 скалярная агрегация в стиле SQL реализована на уровне ядра. Запрос поддерживает операторы « <code translate="no">group_by_fields</code> » и выражения агрегации в формате <code translate="no">output_fields</code>, включая <code translate="no">count(*)</code>, <code translate="no">count(&lt;field&gt;)</code>, <code translate="no">sum(&lt;field&gt;)</code>, <code translate="no">avg(&lt;field&gt;)</code>, <code translate="no">min(&lt;field&gt;)</code> и <code translate="no">max(&lt;field&gt;)</code>. Агрегация выполняется на стороне сервера после фильтрации.</p>
<p>Дополнительные сведения см. в разделе <a href="/docs/ru/get-and-scalar-query.md#Aggregate-Query-Results--Milvus-30x">«Агрегирование результатов запросов</a>».</p>
<h4 id="Null-Vector" class="common-anchor-header">Нулевой вектор</h4><p>Векторы зачастую генерируются асинхронно, поэтому сущность может поступить раньше, чем её вектор. В мультимодальных данных также встречаются естественные пробелы, например, видео без субтитров или товар без изображения. В предыдущих версиях не было оптимального решения: приложения либо откладывали запись до готовности вектора, либо заполняли местозаполняющим вектором, и оба варианта ухудшали качество поиска.</p>
<p>Milvus 3.0 поддерживает значение NULL в векторных полях для всех шести типов векторов. Поиск автоматически пропускает векторы с NULL, качество поиска при этом не ухудшается, а векторы с NULL практически не занимают места в хранилище. В рамках этого изменения также расширяется поддержка функции « <code translate="no">AddField</code> » для векторных полей: с помощью команды ` <code translate="no">nullable=True</code>` существующая коллекция может пополняться новыми векторными полями в режиме онлайн без необходимости перестроения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/nullable-and-default.md">«Поля, допускающие значение NULL</a>».</p>
<h4 id="Custom-Dictionary--Synonym-Dictionary" class="common-anchor-header">Пользовательский словарь и словарь синонимов</h4><p>Готовые токенизаторы не всегда соответствуют требованиям к качеству поиска в производственной среде. Китайский язык, вертикальные области, такие как медицина, право и химия, а также многоязычные корпуса могут существенно выиграть от использования пользовательских словарей и таблиц синонимов. До сих пор эти ресурсы в основном использовались в виде переформулировок запросов на стороне приложения.</p>
<p>В Milvus 3.0 добавлен механизм FileResource для регистрации пользовательских словарей токенизаторов, списков синонимов, списков стоп-слов и правил декомпозиции сложных слов. После регистрации на ресурс можно ссылаться из любого токенизатора или фильтра, и он будет применяться в BM25, анализаторах и Text Match. Теперь словари и синонимы можно версионировать и централизованно управлять ими, вместо того чтобы они были разбросаны по коду приложения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/manage-file-resources.md">«Управление файловыми ресурсами</a>».</p>
<h4 id="Entity-TTL" class="common-anchor-header">Срок хранения сущностей (TTL)</h4><p>TTL на уровне коллекции и на уровне раздела слишком грубы для многих сценариев жизненного цикла и обеспечения соответствия требованиям. Различные арендаторы внутри одной и той же коллекции часто имеют разные правила хранения, и отдельные сущности могут нуждаться в истечении срока хранения по расписанию, которое не совпадает с остальной частью коллекции.</p>
<p>Milvus 3.0 поддерживает TTL на уровне сущностей. Определите поле « <code translate="no">TIMESTAMPTZ</code> » в схеме, отметьте его как поле TTL с помощью свойства коллекции, и Milvus автоматически удалит сущности, срок хранения которых истек. Это позволяет обрабатывать запросы на «право на забвение», удалять данные сеансов по истечении срока и ограничивать историю переписки без необходимости очистки со стороны приложения.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/set-collection-ttl.md#Set-entity-level-TTL--Milvus-30x">«Установка TTL на уровне сущности</a>».</p>
<h4 id="MinHash-DIDO-Doc-in-Doc-out" class="common-anchor-header">MinHash DIDO (Doc-in, Doc-out)</h4><p>В Milvus 2.6 был добавлен индекс <code translate="no">MINHASH_LSH</code> для обнаружения почти-дубликатов на основе наборов, но приложениям по-прежнему приходилось вычислять сигнатуры MinHash перед записью данных в Milvus.</p>
<p>В Milvus 3.0 добавлена функция MinHash, выполняемая на стороне сервера. Определите в схеме поле ввода « <code translate="no">VARCHAR</code> » и поле вывода « <code translate="no">BINARY_VECTOR</code> », привяжите функцию « <code translate="no">FunctionType.MINHASH</code> », и Milvus будет вычислять сигнатуры во время вставки, массовой вставки и поиска. В сочетании с « <code translate="no">MINHASH_LSH</code> » это обеспечивает поддержку рабочих процессов дедупликации для больших наборов данных, создания отпечатков и обнаружения плагиата внутри Milvus.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/minhash-function.md">«Функция MinHash</a>».</p>
<h4 id="EmbList-+-DISKANN" class="common-anchor-header">EmbList + DISKANN</h4><p>Предположение «одна сущность = один вектор» больше не соответствует современному поиску. Длинные документы разбиваются на множество фрагментов, модели позднего взаимодействия, такие как ColBERT, генерируют по одному вектору на каждый токен, а мультимодальные сущности могут иметь несколько представлений.</p>
<p>EmbList хранит список векторов переменной длины для каждого объекта, используя « <code translate="no">DISKANN</code> » в качестве индекса на диске. Использование дискового пути позволяет контролировать загрузку ОЗУ, когда объем корпуса превышает доступный объем памяти. EmbList + « <code translate="no">DISKANN</code> » — это первый вариант из более широкого семейства StructList в данной версии RC. Остальные компоненты семейства, включая фильтрацию StructList и ускорение работы с несколькими векторами с помощью Muvera / Lemur, планируется включить в официальный релиз версии 3.0.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/search-with-embedding-lists.md">«Поиск с использованием списков вложений</a>».</p>
<h4 id="Force-Merge" class="common-anchor-header">Принудительное слияние</h4><p>Производственные рабочие нагрузки со временем приводят к фрагментации сегментов, что вызывает колебания задержки запросов и чрезмерное увеличение объёма хранилища.</p>
<p>В Milvus 3.0 добавлена возможность явно запускать уплотнение сегментов в периоды низкой нагрузки как в синхронном, так и в асинхронном режимах.</p>
<p>Дополнительную информацию см. в разделе <a href="/docs/ru/force-merge.md">«Принудительная уплотнение слияния</a>».</p>
<h4 id="Storage-V3" class="common-anchor-header">Хранилище V3</h4><p>В Milvus 3.0 представлен Storage V3 — столбчатый механизм хранения на основе манифестов, в котором данные и метаданные хранятся в объектном хранилище, совместимом с S3. Каждая версия набора данных фиксируется в виде неизменяемого моментального снимка манифеста — файла в кодировке Avro, в котором фиксируется, какие группы столбцов, дельта-журналы и статистические данные входят в состав набора данных.</p>
<p>Манифесты представляют собой компактные файлы Avro, а дельта-журналы фиксируют удаления на уровне сущностей без перезаписи файлов данных. Это позволяет минимизировать накладные расходы на метаданные по мере роста наборов данных. Манифест также отделяет отслеживание метаданных от пути запроса, что позволяет коллекции управлять большим количеством сегментов без ухудшения производительности запросов.</p>
<p>Поскольку состояния хранятся в объектном хранилище, набор данных является самоописательным: любой читатель, имеющий доступ к пути хранения, может обнаружить и интерпретировать его без центрального каталога. Это свойство лежит в основе интеграции с External Collection, Snapshot и будущими озерами данных.</p>
