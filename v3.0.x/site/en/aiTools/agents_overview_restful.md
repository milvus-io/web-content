## Full prompt

````text
# AGENTS.md for Milvus (RESTful API v2)

Milvus is an open-source vector database for similarity search, hybrid search, and RAG. You interact with it over HTTP through the Milvus RESTful API v2: every request is a `POST` to `${CLUSTER_ENDPOINT}/v2/vectordb/<category>/<action>` with a JSON body.

Use these rules whenever you generate, review, or debug code that calls the Milvus RESTful API on Milvus or Zilliz Cloud. The examples use `curl` and `jq` in bash. The available endpoints and request fields depend on the Milvus server version, so check the user's server version against the version thresholds in these rules before relying on a feature.

## Client & connection

1. **CRITICAL: Always use the `/v2/vectordb/...` endpoints.** Never use the legacy `/v1/vector/...` endpoints: they take different request fields, and a server can turn them off with the `proxy.http.enableV1` setting. If the user provides code that calls `/v1/vector/...`, rewrite it to the matching `/v2/vectordb/...` endpoint and its request fields.

2. **Connection patterns.** Milvus without authentication: the endpoint only, with `TOKEN` left empty or the `Authorization` header omitted. Zilliz Cloud or Milvus with authentication: the endpoint + the header `Authorization: Bearer ${TOKEN}`. Every response carries a `code` field, and failed requests can still return HTTP status 200, so treat any `code` other than `0` as an error.

```bash
# Milvus without authentication
export CLUSTER_ENDPOINT="YOUR_MILVUS_URI"
export TOKEN=""

# Zilliz Cloud or Milvus with authentication
export CLUSTER_ENDPOINT="YOUR_MILVUS_URI"
export TOKEN="YOUR_MILVUS_TOKEN"

curl --request POST \
  --url "${CLUSTER_ENDPOINT}/v2/vectordb/collections/list" \
  --header "Authorization: Bearer ${TOKEN}" \
  --header "Content-Type: application/json" \
  -d '{}'
```

## Schema & data

3. **CRITICAL: Use the exact, case-sensitive `dataType` names.** Write `"dataType": "FloatVector"`, not `"FLOAT_VECTOR"`. The server rejects `"FLOAT_VECTOR"` and `"INT64"` as invalid data types.

4. **CRITICAL: Schema changes are limited.** On Milvus 2.5.x and earlier, the schema is immutable: drop and recreate the collection to change it. On Milvus 2.6 and later, `/v2/vectordb/collections/fields/add` adds a field, and the field must set `"nullable": true`; a field with only a `defaultValue` is rejected. On Milvus 3.0 and later, `/v2/vectordb/collections/fields/drop` drops a field, except the primary key, the partition key, the clustering key, the last vector field, the dynamic field, system fields, fields that a function reads or generates, and the field that the collection's `ttl_field` property names. `/v2/vectordb/collections/fields/alter_properties` changes field properties such as `max_length`. You cannot change the data type of an existing field: create a new collection and migrate the data.

5. **Primary keys: `"Int64"` or `"VarChar"` only.** Composite primary keys are not supported. Primary keys must be unique across the entire collection, including across partitions.

6. **Use `/v2/vectordb/entities/upsert` to update entities.** There is no `/v2/vectordb/entities/update` endpoint. By default, upsert replaces the entire entity if the primary key exists, or inserts a new one. When the primary key field sets `autoID`, still pass the primary key: Milvus 3.0.3 and later keep the key of an existing entity and generate a new key only for rows whose key is not found, which requires the collection to be loaded; earlier versions give every upserted entity a new key generated by the server. To change only some fields of existing entities, set `"partialUpdate": true` in the request body. Use `/v2/vectordb/entities/insert` only when you are certain there are no primary key conflicts.

7. **Define BM25 at collection creation time.** Pass the BM25 function in `schema.functions` of `/v2/vectordb/collections/create`, with a `"VarChar"` input field that sets `"enable_analyzer": true` in `elementTypeParams` and a `"SparseFloatVector"` output field. Adding a BM25 function field to an existing collection with `/v2/vectordb/collections/add_function_field` needs Milvus 3.0 or later with Storage V3 (`common.storage.useLoonFFI`, disabled by default), schema version compaction, and storage version compaction enabled; otherwise the server rejects the request.

## Index & loading

8. **CRITICAL: Index before load, load before search.** A vector field must have an index before the collection can be loaded. A collection must be loaded before any search or query. Shortcut: pass both `schema` and `indexParams` to `/v2/vectordb/collections/create`, and Milvus creates the index and loads the collection. Loading can finish after the create call returns, so poll `/v2/vectordb/collections/get_load_state` until `loadState` is `LoadStateLoaded` before you search. Otherwise call `/v2/vectordb/indexes/create` and then `/v2/vectordb/collections/load`.

9. **Start with `AUTOINDEX`.** Use `"indexType": "AUTOINDEX"` in `indexParams` unless you have specific requirements. Choose HNSW for high recall, DiskANN for larger-than-RAM datasets, IVF_FLAT for memory-constrained scenarios.

## Search

10. **CRITICAL: Every entry of `search` in `/v2/vectordb/entities/hybrid_search` must carry the same number of query vectors.** For one query, put exactly one vector in the `data` of each entry, for example `"data": [[0.1, 0.2, 0.3, 0.4]]`. The server rejects entries with different numbers of vectors ("sub search request nq should be the same"). With more than one vector per entry, the response `data` lists the hits of all query vectors in order, and `topks` gives the number of hits per query vector.

11. **One ranker per `hybrid_search` request.** Send exactly one `rerank` object, such as `{"strategy": "rrf", "params": {"k": 60}}` or `{"strategy": "weighted", "params": {"weights": [0.7, 0.3]}}`. You cannot chain rankers: a `functionScore` with two rerank functions is rejected, and when a request sets both `rerank` and `functionScore`, the server applies `functionScore` and ignores `rerank`. Pick one.

## Quick start

```bash
export CLUSTER_ENDPOINT="YOUR_MILVUS_URI"
export TOKEN="YOUR_MILVUS_TOKEN"

# Exit if a response has a nonzero code
check_code() {
  if [ "$(echo "$1" | jq -r '.code')" != "0" ]; then
    echo "Milvus error: $(echo "$1" | jq -r '.message')" >&2
    exit 1
  fi
}

# 1. Define schema, 2. define index, 3. create collection (Milvus creates the index and loads the collection)
# (dim 4 keeps the example short; use the dimension of your embedding model)
response=$(curl -s --request POST \
  --url "${CLUSTER_ENDPOINT}/v2/vectordb/collections/create" \
  --header "Authorization: Bearer ${TOKEN}" \
  --header "Content-Type: application/json" \
  -d '{
    "collectionName": "docs",
    "schema": {
      "autoID": true,
      "fields": [
        {"fieldName": "id", "dataType": "Int64", "isPrimary": true},
        {"fieldName": "vector", "dataType": "FloatVector", "elementTypeParams": {"dim": 4}},
        {"fieldName": "text", "dataType": "VarChar", "elementTypeParams": {"max_length": 512}}
      ]
    },
    "indexParams": [
      {"fieldName": "vector", "indexName": "vector_index", "metricType": "COSINE", "indexType": "AUTOINDEX"}
    ]
  }')
check_code "${response}"

# Wait until the collection is loaded
for attempt in $(seq 1 60); do
  response=$(curl -s --request POST \
    --url "${CLUSTER_ENDPOINT}/v2/vectordb/collections/get_load_state" \
    --header "Authorization: Bearer ${TOKEN}" \
    --header "Content-Type: application/json" \
    -d '{"collectionName": "docs"}')
  check_code "${response}"
  state=$(echo "${response}" | jq -r '.data.loadState')
  if [ "${state}" = "LoadStateLoaded" ]; then
    break
  fi
  sleep 1
done
[ "${state}" = "LoadStateLoaded" ] || { echo "Collection not loaded after 60 attempts" >&2; exit 1; }

# 4. Insert (the auto ID primary key is omitted)
response=$(curl -s --request POST \
  --url "${CLUSTER_ENDPOINT}/v2/vectordb/entities/insert" \
  --header "Authorization: Bearer ${TOKEN}" \
  --header "Content-Type: application/json" \
  -d '{
    "collectionName": "docs",
    "data": [
      {"vector": [0.1, 0.1, 0.1, 0.1], "text": "first doc"},
      {"vector": [0.2, 0.2, 0.2, 0.2], "text": "second doc"}
    ]
  }')
check_code "${response}"

# 5. Search with Strong consistency so that the new entities are visible;
# Int64 IDs come back as strings so that jq keeps their precision
response=$(curl -s --request POST \
  --url "${CLUSTER_ENDPOINT}/v2/vectordb/entities/search" \
  --header "Authorization: Bearer ${TOKEN}" \
  --header "Content-Type: application/json" \
  --header "Accept-Type-Allow-Int64: false" \
  -d '{
    "collectionName": "docs",
    "data": [[0.15, 0.15, 0.15, 0.15]],
    "annsField": "vector",
    "limit": 5,
    "outputFields": ["text"],
    "consistencyLevel": "Strong"
  }')
check_code "${response}"
echo "${response}" | jq -r '.data[] | "id: \(.id), distance: \(.distance), text: \(.text)"'
```

## Common mistakes

| Mistake | Fix |
|---|---|
| Calling `/v1/vector/...` endpoints | Rewrite with the matching `/v2/vectordb/...` endpoint |
| Searching before the collection is loaded | Pass `indexParams` to `collections/create` and poll `collections/get_load_state`, or call `indexes/create` then `collections/load` first |
| Different numbers of vectors across the `search` entries of `hybrid_search` | Give every entry the same number of vectors in `data`; one vector each for one query |
| Calling `/v2/vectordb/entities/update` | Use `/v2/vectordb/entities/upsert` |
| Adding BM25 after the collection exists | Define the BM25 function in `schema.functions` and `enable_analyzer` at `collections/create` time |
| Upper-case data types (`"FLOAT_VECTOR"`) | Use the case-sensitive names, such as `"FloatVector"` |
| Treating HTTP status 200 as success | Check that the response `code` is `0` |
````
