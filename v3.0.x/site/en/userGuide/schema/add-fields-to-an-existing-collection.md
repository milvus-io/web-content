# Alter Collection Schema

As a collection moves from development to production, its schema often changes. You might add scalar fields such as `source_uri` or `review_status` for filtering and application logic, add a new vector field for embeddings generated by your application, add a BM25 Function and its generated sparse vector field for lexical search over existing text, or remove fields and Functions that are no longer used. Alter Collection Schema lets you make supported field and Function changes in place instead of recreating the collection.

<div class="alert note">

This guide covers schema changes for user-defined fields and for Functions with their generated vector fields in managed collections. To add a field to an external collection, refer to [Alter External Collection Schema](alter-external-collection-schema.md). For field property changes, such as changing `max_length` on a `VARCHAR` field or `max_capacity` on an `ARRAY` field, refer to [Alter Collection Field](alter-collection-field.md). For dynamic field behavior, refer to [Dynamic Field](enable-dynamic-field.md) and [Modify Collection](modify-collection.md).

</div>

## Limits

**Add user-defined fields**

- Added user-defined fields must be nullable. Set `nullable=True` when calling `add_collection_field()`. For existing entities, the added field is `NULL` unless you add a scalar field with a `default_value`.

- Adding user-defined scalar fields is supported in Milvus 2.6.x and later. Adding user-defined vector fields is supported in Milvus 2.6.18 and later.


- Adding StructArray fields is supported in Milvus 3.0.0 and later. Added StructArray fields must be nullable.


- Adding a sub-field to an existing StructArray field is supported in Milvus 3.0.6 and later. The added sub-field must allow element-level null (`nullable=True` on a scalar or vector sub-field, `element_nullable=True` on an array sub-field), cannot have a default value, and cannot be bound to an index in the same request.

- Field names must be unique among fields in the collection.

**Add a Function and its generated vector field**

- Each schema update can add only one Function and one generated vector field.

- The supported Function determines the generated vector field type: `BM25` generates a `SPARSE_FLOAT_VECTOR` field, and `MINHASH` generates a `BINARY_VECTOR` field.

- The generated vector field must be a new field. It cannot point to a field that already exists in the collection schema.

- The generated vector field cannot be nullable.

- The input fields used by the Function must already exist in the collection.

- When adding a BM25 or MinHash Function to an existing collection, the Function input must be a `VARCHAR` field. A `TEXT` input is not supported in this workflow because Milvus cannot backfill the generated output for existing entities from that input type.

**Drop user-defined fields**

- You cannot drop the primary key field, partition key field, clustering key field, or the last vector field in a collection.

- You can drop a whole `ARRAY<STRUCT>` field. Starting in Milvus 3.0.6, you can also drop an individual sub-field by its path, such as `chunks[lang]`, except the last sub-field of the `ARRAY<STRUCT>` field.

- You cannot directly drop a field that is used as a Function input field or generated as a Function output field. To remove a Function output field, drop the Function that generates it.

**Drop a Function and its generated vector field**

- In this schema-change workflow, dropping a Function removes the Function, its generated vector field, and the associated index. The Function input fields remain in the collection schema.

- Dropping a Function is rejected if removing its generated vector field would leave the collection without any vector field.

<div class="alert note">

For schema changes outside supported add and drop operations, recreate or migrate the collection.

</div>

## Add fields and Functions to an existing collection

Choose the workflow based on whether you are adding a user-defined field or a Function that generates a vector field:


- [Add user-defined scalar fields](#Add-user-defined-scalar-fields--Milvus-26x) when you need new metadata for filtering, query output, or application logic.

- [Add StructArray fields](#Add-StructArray-fields--Milvus-300) when you need an array field whose elements share the same Struct schema.

- [Add user-defined vector fields](#Add-user-defined-vector-fields--Milvus-2618) when your application generates embeddings and writes vector values to Milvus.

- [Add a Function and its generated vector field](#Add-a-Function-and-its-generated-vector-field--Milvus-30x) when Milvus should generate vector values from existing fields, such as BM25 sparse vectors or MinHash signatures from text.


- [Add a sub-field to an existing StructArray field](#Add-a-sub-field-to-an-existing-StructArray-field--Milvus-306) when existing Struct elements need a new attribute.


In all cases, the new field name must not already exist in the collection, and the total number of fields cannot exceed the Milvus field-count limit. For details, refer to [Milvus Limits](limitations.md#number-of-resources-in-a-collection).



### Add user-defined scalar fields | Milvus 2.6.x


Use `add_collection_field()` to add a user-defined scalar field to an existing collection.

This differs from storing arbitrary keys in the dynamic field: after the schema update is available, the new scalar field becomes a regular part of the collection schema. You can insert or upsert values into it, create indexes on it where supported, use it in queries and search filters, and return it in query or search output.

Because existing entities were inserted before the new field existed, every added user-defined scalar field must be nullable:

- If you add a scalar field with `nullable=True` and no `default_value`, existing entities return `NULL` for the new field.

- If you add a scalar field with `nullable=True` and `default_value`, existing entities return the default value instead of `NULL`.

Scalar filter expressions do not match `NULL` scalar values. For details, refer to [Nullable Fields](nullable-and-default.md).

### Add StructArray fields | Milvus 3.0.0


Use `add_collection_struct_field()` to add a StructArray field that accepts arrays of Struct elements. To add a StructArray field, do as follows:

1. Create a Struct schema that contains the necessary sub-fields of supported data types. For applicable data types, refer to [StructArray Limits](structarray-limits.md#Supported-subfield-data-types).

1. Reference the Struct schema created above and set the maximum capacity of the field in `add_collection_struct_field()`.

1. Set `nullable=True` in the request.

### Add a sub-field to an existing StructArray field | Milvus 3.0.6

Use `add_collection_field()` with the sub-field path as the field name to add a sub-field to a StructArray field that already holds data. To add a sub-field, do as follows:

1. Name the field with the path `structArrayField[subField]`, such as `chunks[lang]`.

1. Choose a scalar, vector, or scalar array data type supported by StructArray.

1. Set `nullable=True` on the added sub-field. This is required for every added sub-field and is what allows element-level null. On an array sub-field, additionally set `element_nullable=True` to allow null values inside the inner array. The sub-field inherits the row-level `nullable` setting and the `max_capacity` of the StructArray field.

After the sub-field is added, entities that already exist return `NULL` for `chunks[lang]` in each of their Struct elements, and entities whose `chunks` field is `NULL` stay `NULL`. New entities can omit the sub-field or set it to `NULL` in any Struct element.

The following rules apply:

- The added sub-field must be created with `nullable=True`, and an added array sub-field additionally takes `element_nullable=True` to allow null values inside the inner array. It cannot have a default value.

- You cannot bind an index while adding the sub-field. Create the index with a separate `create_index()` call. An added vector sub-field supports element-level metrics only, not `MAX_SIM*`, and the collection must have an index on it before you load the collection with the new sub-field included.

- History segments receive the added sub-field and its index through schema-version compaction. Set `dataCoord.compaction.bumpSchemaVersion.enabled` to `true` (it is `false` by default); otherwise the added sub-field's index does not cover history segments.

- Adding a sub-field to a loaded collection does not release the collection. Queries can return the new sub-field before its index exists.

- Clients that pin a schema timestamp receive a schema-mismatch error and must refresh, as for any added field.

### Add a Function and its generated vector field | Milvus 3.0.x


Use this workflow when Milvus should generate a new vector field from data already stored in an existing collection. The operation adds three related schema elements:

- A Function definition that reads from one or more existing input fields.

- A new vector field that stores the Function output.

- An index definition bound to the new vector field.

For example, a BM25 Function reads an existing `VARCHAR` field and generates a `SPARSE_FLOAT_VECTOR` field for lexical search. A MinHash Function generates a `BINARY_VECTOR` field for near-duplicate detection. This workflow does not add or replace the Function input field.


<div class="alert note">

This feature requires Storage V3. For enablement instructions and compatibility considerations, see [Storage V3](storage-v3.md).

</div>


Adding a Function and its generated vector field to an existing collection also requires schema version compaction and storage version compaction. Milvus rejects the request if either setting is disabled. These additional prerequisites apply only when modifying an existing collection; defining the Function in the initial collection schema does not use this existing-data backfill workflow.


The supported Function determines the generated vector field type:

| Function | Generated vector field type | Typical input field | Typical use case |
| --- | --- | --- | --- |
| `BM25` | `SPARSE_FLOAT_VECTOR` | A `VARCHAR` field with analyzer enabled | Lexical search and keyword relevance |
| `MINHASH` | `BINARY_VECTOR` | A `VARCHAR` field | Near-duplicate detection |

For details about how each Function works, refer to [BM25 Function](bm25-function.md) and [MinHash Function](minhash-function.md).

The generated vector field must not already exist in the collection, and it cannot be nullable. The Function input field must already exist.

## Drop fields and Functions from an existing collection

You can remove user-defined fields directly when they are no longer part of your collection model. To remove a Function and its generated vector field, drop the Function; Milvus removes the generated field and its index in the same schema change.


### Drop user-defined fields | Milvus 3.0.x

Storage cleanup is handled separately from schema cleanup. For details, refer to [When is storage space reclaimed after dropping a field?](#When-is-storage-space-reclaimed-after-dropping-a-field).

To remove the whole StructArray field, drop it by name, as shown in the previous example. After a sub-field is dropped, insert and upsert requests that still carry the sub-field are rejected.

Dropping a sub-field while queries are still running against it can fail transiently: query plans that were built on the older schema keep executing for a short time and fail with an internal error. Finish queries against a sub-field before dropping it, or retry the drop after the running queries finish.

## FAQ

### Which method should I use to add a field or Function?

Use `add_collection_field()` to add a user-defined scalar or vector field.

Use `add_collection_struct_field()` to add a StructArray field when you need an array field whose elements share the same Struct schema.

Use `add_function_field()` to add a Function, its generated vector field, and the bound index definition in the same schema change.

### Why must added user-defined fields be nullable?

Existing entities were inserted before the new field existed, so they do not have values for that field. Setting `nullable=True` lets Milvus represent the missing value as `NULL` until your application writes a value or, for scalar fields, until a default value applies.

This rule applies to user-defined scalar fields and user-defined vector fields added with `add_collection_field()`, and to StructArray fields added with `add_collection_struct_field()`. It does not apply to a Function's generated vector field, which cannot be nullable.

### What happens to existing entities after I add a user-defined field?

For a user-defined scalar field, existing entities return `NULL` unless you set a `default_value`. If you set a `default_value`, existing entities return that default value.

For a user-defined vector field, existing entities have `NULL` for the new vector field. Vector search on the added field skips entities whose vector value is `NULL`. To make existing entities searchable through the new vector field, write non-NULL vector values through upsert or a backfill workflow. New entities can include the new vector field during insert.

For a StructArray field, existing entities return `NULL` for the new StructArray field across all its sub-fields. New entities must provide either `NULL` for the whole field or a valid value for every sub-field in every Struct element, except element-nullable sub-fields in Milvus 3.0.6 and later. For a sub-field added to an existing StructArray field, existing entities return `NULL` for that sub-field in each Struct element.

### Can I add BM25 lexical search to an existing collection?

Yes. If the collection already has a `VARCHAR` field with analyzer enabled, you can add a BM25 Function and its generated sparse vector field for lexical search. In this workflow, Milvus adds the Function, the new `SPARSE_FLOAT_VECTOR` output field, and the bound index definition in the same schema change. You cannot use an existing `TEXT` field as the BM25 input in this schema-change workflow. To use a `TEXT` input, define the field and BM25 Function when you create the collection.

When calling `add_function_field()`, provide an `index_params` object that contains one `SPARSE_INVERTED_INDEX` index with `metric_type="BM25"` for the new output field. Milvus binds the index definition to the generated field as part of the same schema change.

### How do I drop a Function and its generated vector field?

Call `drop_function_field()` with the Function name. In this schema-change workflow, Milvus removes the Function, its generated vector field, and the associated index together while preserving the Function input fields.

### Do I need to wait after altering a collection schema?

Usually, no manual wait is required. If your next operation depends on the updated schema, you can call `describe_collection()` first to confirm the schema that Milvus currently returns.

In a distributed deployment, there can be a short propagation window while Milvus components refresh collection metadata. If an operation immediately after the schema change fails with a schema-related error, refresh the schema and retry the operation.

### Why does an added vector sub-field fail with a FieldNotLoaded error?

After you add a vector sub-field and create its index, queries against the new sub-field can still fail with error 2027 (`FieldNotLoaded`) even though the collection reports ready. Release the collection and load it again; queries then cover the new sub-field.

### When is storage space reclaimed after dropping a field?

Dropping a field removes it from the current schema and normal query/search visibility, but historical data for that field is not physically deleted from object storage immediately.

Storage space can be reclaimed later during compaction. Compaction is a background process that reorganizes existing data files into new, more compact files. After a field is dropped, newly compacted files follow the current schema and omit the dropped field. Milvus does not guarantee an immediate or fixed-time storage-space reduction after dropping a field.

### What happens if I add a scalar field with the same name as a dynamic field key?

If dynamic field is enabled, you can add a scalar field with the same name as an existing dynamic field key. The new scalar field masks the dynamic field key in normal query output, but the original dynamic data is preserved in `$meta`.

For example, if existing entities store a dynamic key named `source`, and you later add a scalar field named `source`, normal output for `source` refers to the scalar field. To access the original dynamic value, use the `$meta` path syntax, such as `$meta["source"]`.
